# 写作工作流

这是一条按需开启的工作流。短稿不要被迫走重流程；长文、观点文、需要研究的内容或用户要求保留中间产物时，再启用本文件。

## 路由

| 路径 | 适用 | 最小产物 |
| --- | --- | --- |
| 轻量改稿 | 已有短稿、事实明确、只要自然化 | 终稿 + 必要的三行说明 |
| 深度长文 | 选题、研究、长文、公众号、观点文、需要反复审稿 | 证据账本、立场、提纲、版本稿、审校结果、终稿 |
| 检测评分 | 用户要先检测、量化、比较版本或批量扫描 | 检测报告，不自动改写 |
| 风格学习 | 用户提供样本并要求学习作者/本人写法 | 证据账本、风格规则、验证短文；不是把样本原句拼成模板 |

## 深度路径

### 0. 任务契约

确认体裁、读者、作者意图、语气、篇幅、来源截止时间、不可改事实、是否允许联网和需要哪些交付文件。能用保守默认值解决的，不停下来做问卷。

### 1. 材料与证据账本

先把材料分成：原始事实、当事人自述、二手转述、作者推断、未知或争议。每一条重要主张记录：

| 字段 | 内容 |
| --- | --- |
| `claim` | 准备写进正文的主张 |
| `source` | 文件、URL、数据表、访谈或用户原话 |
| `source_type` | 一手、自述、二手、推断、未知 |
| `time_scope` | 来源时间和适用截止时间 |
| `status` | confirmed、attributed、inferred、needs-user-source、cut |
| `notes` | 口径、冲突、限制和不能外推的范围 |

没有证据的精确数字、人物动作、现场细节和心理活动不能进入事实稿。来源冲突不强行调和，保留冲突并说明影响。

### 2. 立场与提纲

先写一句可检验的主判断，再写读者为什么现在需要它。把提纲按信息推进组织，而不是按“背景、意义、展望”的万能模板组织。每个段落标记它是在提供事实、解释机制、给例子、提出限制还是做判断；相邻段落只做同一件事时合并或删除。

### 3. 初稿与版本

保留信息，不保留机械形状。可以合并、拆分、改序，但不得丢掉数字、名称、条件、责任边界和来源归属。初稿、内部备注和事实账本分开保存，不把“修改说明”“AI 检查结果”混进正文。

### 4. 编辑审校

按 [review.md](review.md) 做六遍检查，再用 [reader-test.md](reader-test.md) 做独立角色检查。编辑阶段优先解决事实外延、论证推进、低信息句和读者不信，不用口头禅、错别字和空泛故事制造人味。

### 5. 去痕与声音

先读取场景和语气文件，再读取 [patterns-zh.md](patterns-zh.md) 或 [patterns-en.md](patterns-en.md)。按“成组模式优先、上下文决定、保留真人细节”的顺序修订。用户要求“先检测”时，检测报告和改写必须分开；用户只要成稿时，不展示内部报告。

### 6. 事实核查门

最终正文变动后重新核对证据账本。至少检查数字、日期、名称、链接、引用归属、产品能力、政策适用范围和建议的条件。红色问题包括：与来源矛盾、链接失效、需要用户补充来源、把推断写成事实。红色问题未处理时，不生成“已核实终稿”。

### 7. 交付与复盘

按用户要求交付正文、来源、版本差异、事实报告或格式文件。长文项目可使用以下命名，但不强制创建完整项目树：

```text
draft_v1.md
draft_v1_notes.md
evidence_ledger.json
fact_claims.json
fact_check_report.md
draft_final.md
draft_final_clean.txt
episode.md
```

最后记录哪些修改真正改善了信息、可信度或读者理解，哪些规则没有启用以及为什么。没有实际差异时也记录“无变化”及原因，不伪造复盘成果。

## 停机与自动推进

- 如果下一步会改变选题、主判断、作者声音、事实边界、是否配图或输出格式，先让用户选择。
- 如果只是确定性检查、按已确认约束修复、重新读取文件或生成同一版本的配套产物，可以连续完成，不重复询问“是否继续”。
- 不强制展示 A/B/C 菜单。用户已给出明确目标时直接执行；只有缺少选择会显著改变交付时才提问。
