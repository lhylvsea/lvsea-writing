# Sloptrim 适配说明

本文件说明 `lvsea-writing` 对 [seyedehsanhadi/sloptrim](https://github.com/seyedehsanhadi/sloptrim) 的二次吸收。审阅版本为 `v0.9.4`，固定 revision 为 `38dbb7cb4e97de0b9bf157903c95bdcab016dda2`，上游许可证为 Apache-2.0。这里只吸收可解释的编辑流程和风险边界，不复制上游 `SKILL.md`、英文规则库、检测器实现、钩子或运行时依赖。

## 取舍

| 决定 | 吸收或排除的内容 |
| --- | --- |
| 保留 | 完整成稿后再检测；按模式族分层，而不是看到一个词就重写；保护数字、名称、引语、引用、占位符和技术复合词；最多两轮反查；把字符层残留与语义问题分开。 |
| 改造 | 上游的 `ai_tell_score` 改成中文优先的 `review_score`；用现有 `scripts/check_writing.py` 的可读中文发现替代英文词表；加入 `review_band` 和 `review_confidence`，只作为编辑分流信号。 |
| 不采用 | Claude 专属安装和钩子、自动改写或静默覆盖文件、英文阈值直接迁移到中文、富文档重建、外部检测服务、任何“通过检测”的承诺。 |
| 新增 | 与 `lvsea-writing` 的单入口路由对齐：资料和结构先成立，检测只在完整初稿之后介入，最后仍由 Humanizer 适配和作者人工终审收口。 |

## 推荐顺序

```text
资料/证据 -> 主判断/提纲 -> 读者/声音/场景 -> 完整初稿
-> scripts/check_writing.py 复查 -> 定点语义修改 -> 再复查
-> 最后 Humanizer 适配 -> 事实回查 -> 作者人工终审
```

检查器不会自动改稿。用户说“先检测”时，先交付报告，再等待或按用户指定范围修改；用户只要终稿时，内部完成复查，不把分数、规则名和过程说明塞进正文。

## 分段只用于分流

检查器输出 `review_score`（0–100）、`review_band` 和 `review_confidence`。分段名称借鉴上游的可读标签，但不是同一算法、不是校准后的概率，也不能与其他检测器横向比较：

| 分段 | 默认动作 |
| --- | --- |
| `clean`（0–20） | 只处理确认存在的机器残留或字符问题，不为追求分数重写。 |
| `light_tells`（21–40） | 针对命中句做最小修改，保留原作者节奏。 |
| `mixed`（41–60） | 先看模式是否成组出现，再做语义编辑；不能只删词。 |
| `heavy_tells`（61–80） | 回看材料、主线和声音，必要时退回结构阶段，不直接把全文压平。 |
| `pervasive_tells`（81–100） | 优先确认输入是否是模型过程稿、复制残留或错误格式；分数本身不能批准整篇重写。 |

置信度会覆盖分段带来的冲动：`none` 表示正文很短，`low` 表示单个句式可能影响结果，`usable` 才适合定点复查，`solid` 才可以辅助选择复查深度。正式材料、引文、代码、列表、双语稿和高度专业化文本都要降低对统计信号的依赖。

## 保真门

每一轮修改后都要回查：

- 数字、单位、日期、名称、链接、引语和引用归属；
- 谁在陈述、谁被引用、哪些地方仍然是推测或带条件的判断；
- 否定、排名、同时发生的关系，以及数字所修饰的对象；
- `[Name]`、`{{first_name}}`、`[待补充]` 等占位符；
- 技术复合词和代码、表格、Markdown 结构；
- 重写后的长度不超过输入的 1.25 倍，除非用户明确要求扩写。

发现来源冲突、事实缺口或作者判断被改动时，停止去味，回到证据账本或交给作者决定。不能用口头禅、错别字、虚构故事或“嗯、其实吧”制造人味。

## 格式与验证边界

`scripts/check_writing.py` 面向 Markdown/纯文本，能够遮罩代码、链接和前置元数据；它不重建 DOCX、PPTX、XLSX、PDF 或 EPUB。富文档需要在格式感知的编辑器中修改，再对导出的文本副本做复查，不能把检查器输出覆盖回原文件。

```powershell
$env:PYTHONUTF8 = '1'
python scripts/check_writing.py path\to\draft.md --scenario professional --json
```

脚本返回码只对高置信复制残留和助手式框架失败；警告仍需结合体裁、来源和作者声音判断。静态检查、触发回归和本地测试只能证明包和规则可运行，不能证明文本由谁写成、能否通过平台判定或已经获得作者认可。
